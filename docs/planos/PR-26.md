# Plano — PR-26 · PWA instalável

Branch: `feature/pr-26-pwa` (base: 8b7f2f8, a main após o PR-03). Pacote de trabalho único: **frontend**. Nenhum backend.

## 1. Objetivo
Cumprir do RF-15 a parte "PWA instalável" e "offline para biblioteca e treinos já vistos": manifest em pt-BR, ícones 192/512 (any e maskable), service worker com pré-cache do app shell, stale-while-revalidate só para GET de exercícios e treinos, aviso de nova versão com atualização explícita, limpeza dos caches ao encerrar a sessão e /eu nunca cacheado. Nesta branch as telas ainda são espaços reservados (as frentes 04–21 constroem em paralelo); o PWA é sobre manifesto, ícones, service worker, instalação e atualização.

## 2. Contrato
Nenhuma rota nova ou alterada na API; docs/API.md e docs/MODELO-DE-DADOS.md não mudam. O que muda é o tratamento, no cliente, das requisições que passam pelo service worker (só no build de produção):

| Requisição | Tratamento no service worker (frontend/vite.config.js) |
|---|---|
| Assets do build (HTML, JS, CSS, SVG, PNG, ICO, webmanifest) | pré-cache do app shell (`globPatterns`); `cleanupOutdatedCaches` |
| Navegação (HTML do SPA) | `navigateFallback: 'index.html'`, exceto `/api/`, `/sanctum/`, `/docs`, `/up` e `/pulse` (`navigateFallbackDenylist`) |
| GET mesma origem `/api/v1/exercicios`, `/api/v1/exercicios/{id}`, `/api/v1/treinos`, `/api/v1/treinos/{id}` (qualquer query string) | `StaleWhileRevalidate`, cache `api-biblioteca`, só respostas 200 (`cacheableResponse.statuses: [200]`), até 200 entradas por 7 dias |
| GET `/api/v1/eu` e tudo abaixo, `/sessoes`, `/estatisticas`, `/agendamentos`, `/treinador`, `/referencias`, `/saude` | sem rota no service worker: vai direto à rede, nunca entra em cache |
| POST, PUT, PATCH, DELETE | só rede (a rota de cache é `method: 'GET'`) |
| `/sanctum/*`, `/docs/*`, `/up`, `/pulse` | fora do fallback e sem cache |

Regras do cache de API: 401/403/404/422/429/5xx nunca são gravadas; offline, uma rota não vista antes falha como erro de rede e a tela mostra o estado de erro. Com rede, o 401 revalidado segue o fluxo do http.js.

Manifest (`manifest.webmanifest`, gerado pelo plugin): `name` e `short_name` "VOLLEY PRO", `description`, `lang` "pt-BR", `dir` "ltr", `start_url` "/", `scope` "/", `id` "/", `display` "standalone", `orientation` "portrait", `background_color` e `theme_color` #0E0E0E (token `fundo`), ícones `/icones/icone-192.png` e `/icones/icone-512.png` (`purpose: any`) e `/icones/icone-maskable-192.png` e `/icones/icone-maskable-512.png` (`purpose: maskable`). O index.html traz `<meta name="theme-color">`, `<link rel="icon">` (SVG) e `<link rel="apple-touch-icon">`; o `<link rel="manifest">` é injetado pelo plugin no build.

Registro: `registerType: 'prompt'` e `injectRegister: false`; quem registra é `src/app/AtualizacaoDoApp.jsx` via `virtual:pwa-register/react` (`useRegisterSW({ immediate: true })`). Em dev e nos testes o módulo virtual é o registro vazio do plugin (`devOptions` desligado), então o proxy `/api`, `/sanctum` e `/docs` do Vite nunca passa pelo service worker.

## 4. Regras de negócio aplicáveis
- RN-11 (cada um só acessa os próprios dados): o servidor não muda; o cache só guarda o que as Policies já autorizaram para aquele usuário. No cliente, `limparCachesDoApp()` (src/lib/pwa.js) apaga todos os caches `api-*` e é chamada pelo http.js em todo 401; `encerrarSessaoLocal(queryClient)` limpa também o TanStack Query e fica pronta para o módulo de auth (PR-05) chamar no sucesso de "sair" e no DELETE /eu. /eu nunca é cacheado.
- RN-06 e RN-07: stale-while-revalidate pode mostrar por um carregamento um item já excluído ou que perdeu visibilidade; a revalidação corrige na leitura seguinte (pendência registrada no ESTADO).
- RN-13: o botão "Atualizar" chama `updateServiceWorker(true)` (skipWaiting + recarga); não há botão "Instalar" próprio.

Build: `npm --prefix frontend run build` gera `dist/sw.js`, `dist/workbox-*.js` e `dist/manifest.webmanifest`; conferir no sw.js a `NavigationRoute` com a denylist e a rota `StaleWhileRevalidate` com `CacheableResponsePlugin({ statuses: [200] })`.

Só no navegador (Chrome/Edge com o build servido por `vite preview`): oferta de instalação (DevTools > Application > Manifest sem erros) e a troca real de versão (novo build → aviso → Atualizar). Playwright: `e2e/pwa.spec.js` quando a infraestrutura do PR-05 existir, contra o `vite preview`.

## 7. Telas e estados
- Aviso de nova versão: "Nova versão disponível." com "Atualizar" e "Depois"; alvos de 44 px (Botao md); fixo no topo para não cobrir a NavInferior nem o botão principal do treino; `role="status"` sem roubar o foco; não some por tempo (WCAG 2.2.1).
- Offline com dado em cache: a tela mostra os dados (indicador de conexão é do PR-27). Offline sem cache: erro de rede com o texto do `descreverErro` (texto próprio fica para quando as telas existirem).
