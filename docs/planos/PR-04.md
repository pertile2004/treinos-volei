# Plano — PR-04 · Cadastro de usuário, Termos e Privacidade

Branch: `feature/pr-04-cadastro` (base: PR-01 e PR-03). Pacotes de trabalho: **backend**, **frontend**, mais a camada de dados adiantada (migration, model e factory de `users`).

## 1. Objetivo
RF-01 (cadastro com nome, e-mail, senha, papel e aceite dos termos) e RF-16 (páginas de Termos de Uso e Política de Privacidade). Cadastro válido cria a conta, inicia a sessão (Sanctum SPA, cookie) e leva à tela inicial, ainda provisória.

## 2. Contrato

### POST /api/v1/auth/cadastro
- Público (sem autenticação). Exige CSRF: o front chama antes `GET /sanctum/csrf-cookie`.
- Rate limit: limitador `cadastro`, 10 requisições por minuto por IP (`throttle:cadastro`). Requisições inválidas também contam.
- O e-mail é aparado e passado para minúsculas antes de validar e gravar (o PostgreSQL diferencia maiúsculas no índice único).

| Campo | Regras | Mensagem (422) |
|-------|--------|----------------|
| nome | obrigatório, string, 2 a 100 caracteres | "Informe seu nome (mínimo de 2 caracteres)." · "O nome pode ter no máximo 100 caracteres." |
| email | obrigatório, e-mail válido, máximo 255, único em users.email | "Informe um e-mail válido." · "O e-mail pode ter no máximo 255 caracteres." · "O e-mail já está em uso." |
| password | obrigatório, string, mínimo 8 (RN-12), confirmado | "A senha precisa ter no mínimo 8 caracteres." · "As senhas não conferem." |
| password_confirmation | igual a password | (o erro sai em `password`) |
| papel | obrigatório, enum Papel só com `jogador` e `treinador` (`admin` → 422) | "Escolha entre jogador e treinador." |
| aceite_termos | obrigatório, regra `accepted` | "Você precisa aceitar os termos." |

Os nomes `password` e `password_confirmation` são a exceção de framework do CLAUDE.md (casam com a regra `confirmed`). `meta_semanal`, `codigo_convite` e `treinador_id` enviados pelo cliente são ignorados.

Resposta 201 (`UsuarioResource`):
```json
{ "data": { "id": 1, "nome": "Ana Souza", "email": "ana@example.com", "papel": "jogador", "meta_semanal": 3, "data_nascimento": null } }
```
Nunca inclui `password` nem `remember_token`. A resposta traz o cookie de sessão (sessão regenerada) e o usuário já está autenticado no guard `web`.

Erros:
- 422: `{ "message": "O e-mail já está em uso.", "errors": { "email": ["O e-mail já está em uso."] }, "request_id": "..." }` (uma ou mais chaves em `errors`).
- 429: `{ "message": "Muitas tentativas. Tente de novo em instantes.", "request_id": "..." }` (handler do PR-01).
- 419: CSRF ausente ou expirado (o http.js repete uma vez).
- 401, 403 e 404 não se aplicam (rota pública, sem recurso de outro usuário).

/termos e /privacidade são páginas do SPA, sem API.

## 3. Modelo e migration (commit-semente d2cb5e5)
`2026_11_06_200400_alterar_users_para_o_dominio.php`: `name` → `nome` varchar(100); `papel` varchar(20) não nulo com índice (sem padrão no banco); `meta_semanal` smallint padrão 3; `data_nascimento` date nula; `codigo_convite` char(8) nula única; `treinador_id` FK → users nula, ON DELETE SET NULL, com índice. `down()` desfaz na ordem inversa.

Model `User`: `#[Table('users')]`, `#[Fillable(['nome', 'email', 'password', 'papel', 'meta_semanal', 'data_nascimento'])]`, `#[Hidden(['password', 'remember_token'])]`; casts papel → `App\Enums\Papel`, data_nascimento → date, password → hashed, meta_semanal → integer; relações `treinador()` e `atletas()`. `codigo_convite` e `treinador_id` ficam fora do Fillable (só services gravam). `UserFactory` usa `nome` e `papel` jogador por padrão. Teste: `backend/tests/Feature/ModeloDeDados/UsersTest.php`.

## 4. Regras de negócio garantidas no servidor
- RF-01 / papel: `Rule::enum(Papel::class)->only([Jogador, Treinador])`; o Service grava só nome, email, password e papel.
- RN-12: `min:8`; hash pelo cast `hashed`; nenhum bloqueio de colar no CampoTexto.
- RN-14: nenhuma validação de idade; `data_nascimento` não é pedida e nasce nula (limitação no README e na Privacidade).
- RN-11: a resposta devolve só o usuário recém-criado. RN-13: sem login social. RN-05: `codigo_convite` nasce nulo (PR-22).
- Sessão: `CadastroService` recebe `Illuminate\Contracts\Auth\StatefulGuard` (binding → `Auth::guard('web')` no AppServiceProvider) e faz `login()`; o Controller regenera o id da sessão quando a requisição tem sessão (statefulApi do Sanctum: Referer ou Origin em `sanctum.stateful`).
- Aceite dos termos: só a regra `accepted`; não é persistido (sem coluna no modelo) — pendência no ESTADO.md.
- Policy não se aplica (rota pública).

## 8. Riscos e limites conhecidos
- O fluxo real navegador → API (csrf-cookie e cookie de sessão persistido) não foi exercitado nesta máquina; a evidência de "logado" é o Pest (`assertAuthenticatedAs` e cookie na resposta). O E2E do PR-05 fecha a lacuna.
- O frontend não guarda o usuário do 201 no cache do TanStack Query (chave `['eu']` nasce no PR-05).
- Usuário já logado chamando o cadastro cria outra conta e troca a sessão (sem regra nos docs).
- O 429 usa o cache (CACHE_STORE=database); nos testes o RefreshDatabase isola o contador.
